# 并发评估、缓存与失效

## 1. 缓存键

缓存（`resultcache.Cache[*Decision]`）是泛型、并发安全的，键由三部分组成：

```
Key = (PolicyVersion, ImageRef, RequestFingerprint)
```

- `PolicyVersion`：当前生效策略版本（外部策略的 `version`，或内置 `builtin-v1`）。
  策略更新后版本号变化，**旧结论在新键下天然不可见**。
- `ImageRef`：镜像引用，不同镜像的结论互不串用。
- `RequestFingerprint`：对元数据（apiVersion/仓库/标签/摘要/摘要算法等）与
  全部签名、证明输入一起做 SHA-256 指纹。即使引用相同，清单内容变化或携带的
  签名/证明不同，也会得到不同的键，**不会错误复用结论**。

## 2. 允许与拒绝都缓存，拒绝永远是拒绝

- 最终结论（允许或拒绝）原样缓存，拒绝结论携带原因码与判定轨迹。
- 缓存命中时返回的是被缓存的结论副本，调用方拿到的拒绝结论**不会被改写成通过**。
- 非终态的内部错误不缓存，避免把偶发故障固化成错误结论。

## 3. 并发合并（singleflight）

`Guard.Evaluate` 对同一缓存键的并发调用做合并：只有一个 goroutine 真正执行
判定，其余 goroutine 等待同一份结论。因此并发请求看到的判定依据与结果完全
一致，且缓存中只会有一条合并后的条目（测试
`TestConcurrentEvaluationConsistentAndCached` 覆盖 64 并发）。

## 4. 失效规则

- **策略重载**（`Guard.Reload`）：先完整加载并校验新策略，成功后原子切换
  版本并 `Clear()` 整个缓存——新版本下绝不复用旧结论。
- **重载失败**：保留旧策略继续服务，旧缓存不动；失败原因向上返回，不会出现
  “加载了一半”的策略。
- **镜像清单变更**：引用相同但元数据指纹变化即产生新键，旧键自然失效；
  也可通过 `Cache.Clear()` 手动清空。

## 5. 关键不变量（测试覆盖）

- 同键并发评估结论一致，且只产生一条缓存条目；
- 被缓存的拒绝结论在再次查询时仍为拒绝（原因码不变）；
- 策略版本推进后缓存被清空，相同输入在新策略下重新判定；
- 签名/证明输入不同（如同镜像不同签名）不会命中彼此的缓存。
